# 07 · 产品经理评审 · 锦鲤 PRD（dsh-koi）

> 2026-10-24。评审对象：`docs/05-锦鲤预测.md`（v1 PRD，主评审对象）+ `docs/06-锦鲤心智-方案与待拍板问题.md`（v2 认知层方案，作为上下文）。
> 评审基准：单人 hobby 项目、阿里云 2核2G 单机、v1 代码就绪待部署、v2 在设计阶段。评审独立于 06 的 Q1–Q13，只引用不复述；新增决策点用 **N1…N6** 编号，与 Q 系列并行拍板。

## 一、总评：4 / 5

| 维度 | 分 | 一句话 |
| --- | --- | --- |
| 定位与诚实条款 | 5 | 「账本难看是功能不是 bug」+ 五条自举纪律，是这个项目最值钱的部分，多数正经团队都写不出这种清醒 |
| 范围控制 | 5 | v1 明确不做的四条边界 + 面板只留一个按钮，克制得很好 |
| 技术方案 | 4 | 选型整体正确且贴预算，但核心判奖算法缺测试护栏，文件并发写有隐患 |
| 失败路径完整性 | 3 | 成功路径验收三步很清楚，但「推送失败重试」「休市日」「静默挂掉怎么被发现」没定义——而按时送达恰恰是这个产品的核心承诺 |
| 文档即运维 | 4 | 排障表和 runbook 是加分项；契约 schema 没落纸是缺口 |

**三句定位评价**：这不是一份「需求文档」，是一份「设计+部署+运维」三合一的工程文档——对单人项目这是优点，不必改。真正的产品风险不在技术，在叙事：产品名「预测」、人设「小财迷」、带置信度的完整分析，每个行为都在暗示「她能预测」，与诚实条款有内在张力，需要在展示层化解（见 P1-H）。v2 方案的野心远大于 v1，最大的实施风险是 token 成本失控和时间线膨胀，需要硬护栏而不是自觉（P1-B、P1-C）。

## 二、P0 · 上线前必须解决

| # | 问题 | 为什么重要 | 建议 |
| --- | --- | --- | --- |
| P0-1 | **对账匹配键未定义，休市日会错账**。PRD 只说「22:00 抓开奖→判奖」，没说按什么匹配。若按「最新一期」对账，遇春节休市/官方调整停售，会把预测对着错误期号判奖或连日报错 | 账本是「唯一记分口径」，一次错账污染的是整个诚实条款的公信力，且事后难清洗 | ① 对账必须按**期号精确匹配**（出号时记录目标期号，开奖后只认这个期号）；② 抓不到对应期号时状态机进「休市/未开奖」分支，静默顺延，不算失败不发致歉；③ 春节休市期间预测照出没关系，但对账必须挂起。→ 需拍板 **N1** |
| P0-2 | **复式拆注判奖是自研核心算法，却没有金样本测试**。红8+蓝1=C(8,6)×28 注逐注判级，六等奖「蓝中即有」（0/1/2红+蓝）、四等五等的红数分界，全是易错边界 | 判错一个奖级 = 账本系统性失真，而且不报错、难察觉；这算法还要被 v2 复盘引擎当真值依赖 | 上线前拿历史真实开奖构造覆盖全部奖级的假想投注，做成回归测试进 `tools/koi.mjs`（如 `koi.mjs selftest`），验收三步变四步 |
| P0-3 | **推送失败的重试与补发语义未定义**。17:30 时刻 NapCat 挂了怎么办？19:00 恢复了会补发吗？还是标记失败就此放弃？「19:50 放弃并致歉」——但致歉消息本身也走 NapCat，通道全挂时连致歉都发不出 | 「按时送达」是产品核心承诺，失败语义不清 = 承诺的兑现条件不清 | 定义：推送失败按 5min 间隔重试至 catchUpEnd；面板常驻「未送达」红标；通道恢复后自动补发并标注「补发」；致歉改落盘+面板展示兜底，不依赖通道活着。→ 需拍板 **N3** |
| P0-4 | **静默失败无法被发现**。dsh 进程死了、接口改版了、agent 会话卡死了——所有排障都假设「主人主动去看面板/journalctl」，但这个系统唯一的主动触达就是那条消息本身，它沉默时主人只能靠「今晚怎么没消息」事后发现 | 单人系统没有告警渠道，「没消息=坏消息」可以接受，但至少要把「新鲜度」变成可查的主动信号 | ① `deps` 体检里加**数据新鲜度探针**（最近一期开奖距今 >7 天 = 告警）；② 战果消息天然是每日心跳，运行手册里写明「当晚 22:30 前没收到任何消息 = 系统出事，看 journalctl」 |
| P0-5 | **文件契约 schema 没有落纸**。整个三道保险建立在「她写结构化 JSON→硬校验」上，但字段清单、类型、枚举、版本号在哪？只在代码里 | ① 校验失败时无法快速定位是哪个字段违规；② v2 预注册档案要导入 v1 的 predictions.json，schema 不冻结则 M1 迁移是盲迁 | PRD 增补一节「契约 schema v1」：字段/类型/必填/枚举，加 `schemaVersion` 字段；此文档就是 v1→v2 的迁移依据 |
| P0-6 | **上线前必须确认：定时任务复用 `koi-lottery` 会话，上下文会无限增长**。每期开奖都唤醒同一个会话，13 期/周的分析文本全部滚入历史——token 成本逐月爬升，且旧推理会污染新推理（和「每期独立随机」的定位背道而驰） | 成本爬升是慢性的，上线三个月后才发现就要清史；上下文污染直接违背诚实条款精神 | 确认 DSH 对会话有无自动压缩/截断；若无，定时出号改为「每期新开会话 + 显式注入模板（人设+近 N 期摘要）」，`koi-lottery` 常驻会话只留作主人闲聊。→ 需拍板 **N5** |

**验收三步建议扩为五步**：现有 1–3 保留，加「4. 杀掉 NapCat 跑一期，验证未送达标记与补发」「5. 对账中途 `systemctl restart dsh`，验证状态机恢复不重复记账」——「重启不乱」是宣称的保险 ②，宣称就该被测。

## 三、P1 · v2 设计中要解决（技术选型与实施）

| # | 主题 | 判断与建议 |
| --- | --- | --- |
| P1-A | **存储演进与文件所有权** | JSON→SQLite 方向正确（呼应 Q2/Q9）。但要补一张**所有权矩阵**：koi / koi-mind / tools CLI / 主人手工，各自对哪个文件只读、哪个可写。现在 `state.json/predictions.json/ledger.json` 与手工 `settle` 命令就已在并发写，v2 两个插件共库后风险放大。所有写盘改**临时文件+原子 rename**，SQLite 开 WAL。图归属建议：koi 独占自己的三个 JSON，koi-mind 独占 SQLite，中间靠导出同步 |
| P1-B | **token 预算硬顶与自动降档** | Q6 估了周消耗（70–130 万标准档），但没有月度上限和超限行为。中奖不是 KPI，那花在负期望游戏上的真金白银必须有硬顶：**月度预算超限→标准档降轻量档→再超→单 agent 出号**，降档动作写进代码而非靠主人看账单。→ 需拍板 **N2** |
| P1-C | **多 Agent 时间线硬化** | v1 承诺 18:00 前送达；v2 时间线 17:30 注入记忆→多 agent 提案→互评→修订→合成，全是 LLM 调用，轮数不设上限就是定时炸弹。建议：每轮显式 timeout、总预算 **25 分钟**，超时自动降级为「数据官+单策略师」，再超时走 v1 兜底。另外路线图上 M3 的「记忆注入」依赖 Q3 的记忆插件选型——Q3 建议**现在就拍板**（auto-memory 起步），别等到 M4 |
| P1-D | **随机基线也要预注册** | 纪律 2 说基线同行，纪律 1 说预注册，但没明说基线号的登记时点。基线若在开奖后补录，「无事后选择」对基线自身就破防了。基线号与预测号**同一时刻落盘**，这是纪律体系的锚点，成本为零 |
| P1-E | **自评反自欺要结构化** | 周报里「分析纪律自评」若是 LLM 自由发挥，等于让被审计者自己写审计报告。自评改为**结构化清单**：五条纪律逐条 yes/no + 证据指针（档案 ID），LLM 只填表不写散文 |
| P1-F | **图谱外键从 M2 就埋** | Q9 选 SQLite 起步正确。但 M5 投影语义时空图需要「卡片ID×因子ID×期号×事件」的边数据——若 M2/M3 产出时不记录这些外键，M5 时历史边已永久丢失。原则：**现在记录、以后投影**，M1 表结构里就把外键留好 |
| P1-G | **2G 内存预算** | 账面：DSH 宿主 + NapCat 容器 + 可选 130MB 本地嵌入模型 + M2 全量回测的 CPU 峰值，已经很紧。建议：嵌入模型默认关（M4 再评估）；回测任务**错峰跑**（17:00–22:30 开奖敏感窗口禁止重计算）；SQLite 查询加 LIMIT 养成习惯 |
| P1-H | **置信度的叙事张力** | v2 推送带「置信度」——对独立随机事件显示置信度是剧场化的误导，与诚实条款冲突。建议：置信度**入档案不进推送文案**；推送模板常驻一句人设内的话点破「这是随机游戏，账本难看是常态」。→ 需拍板 **N6** |
| P1-I | **备份** | ledger.json + predictions.json 是整个项目的海马体，「预注册不可改」的前提是**不会丢**。每周 tar 一份到异目录（或主人自选的 git 私库/邮箱），写进 runbook。→ 需拍板 **N4** |

| P2-5 | 排列三取排列五前三位 | 同机同期摇号的假设成立且已实测 ✓；保留，但在 runbook 加一条「每季度人工抽 3 期与官方排列三公告核对」 |

## 五、建议新增拍板问题（与 Q1–Q13 并行）

### N1. 对账匹配键与休市处理
出号时记录目标期号，对账只认该期号；抓不到时进「休市/未开奖」静默顺延分支。**建议**：按期号匹配（这是唯一正确答案，拍板只是确认）。
**答复**：**采纳：期号精确匹配 + 休市日历静默顺延**（2026-10-24 需求引出会话拍板；阶段A于同日回填，原讨论会话不可检索，记录源=docs/12 §5.1）。落地条目：docs/12 FR-001/FR-002/DC-006/DC-007。

### N2. token 月度预算硬顶
标准档周耗 70–130 万 token 的量级下，**建议**：先设月度 300 万 token 硬顶，超限自动降轻量档、再超降单 agent；跑一个月后按实际账单调整数字。
**答复**：**500 万 token/月硬顶**（2026-10-24 需求引出会话拍板；阶段A回填，记录源=docs/12 §5.1）。⚠ 高于本文档建议的 300 万。机制修正见 docs/12 BC-013/FR-046：预算耗尽当月以兜底档收口（单agent 非终点）+ 月度自动重置。

### N3. 推送失败重试策略
**建议**：5 分钟间隔重试至 catchUpEnd；面板标「未送达」；通道恢复自动补发并标注；致歉落盘+面板展示，不依赖通道。
**答复**：**采纳建议语义**（2026-10-24 需求引出会话拍板；阶段A回填，记录源=docs/12 §5.1）：5 分钟间隔、分类终止线（预测至 catchUpEnd、战果/致歉至 23:30）、超线转补发队列；细化见 docs/12 FR-005。

### N4. 备份去向
**建议**：每周 tar ledger+predictions 到 `/home/dsh/.dsh/koi-backup/`（保留 8 份），另有意愿可加 git 私库。
**答复**：**周备份保留 8 份 + 至少每月 1 次出箱**（2026-10-24 需求引出会话拍板；阶段A回填，记录源=docs/12 §5.1）：v2 认知层资产全部纳入备份清单（docs/12 FR-048）。

### N5. 17:30 定时任务会话策略
**建议**：确认 DSH 压缩机制；倾向「每期新会话 + 显式注入模板」，常驻会话留作闲聊。
**答复**：**每期新会话 + 显式注入模板，koi-lottery 常驻会话留闲聊**（2026-10-24 需求引出会话拍板；阶段A回填，记录源=docs/12 §5.1）：时点 M3，docs/12 FR-054；M0–M3 过渡期沿用现状 + 运行手册检查项。

### N6. 置信度是否进推送文案
**建议**：不进。入档案供复盘，推送文案保持「完整分析 + 这是随机游戏」的诚实基调。
**答复**：**采纳：置信度只入档案不进推送文案**（2026-10-24 需求引出会话拍板；阶段A回填，记录源=docs/12 §5.1）：离散档位（低/中/高）、禁百分比（docs/12 BC-007/FR-027/DC-008）。
